# platform-redesign：需求确认

Status: ready-for-agent（D1–D7 已定，架构文档与 ADR 已按 2026-11-21 审查修订，任务单已按九类拆到各分类目录，总览见 map.md）
确认日期：2026-11-20

## 用户要的是什么

把 Talaria 从“一个整体工作台 + 规划中的交易流水线”，改成**按产品功能组织、可按需组合的本机交易研究平台**，体验参照 TradingView：

- 行情数据、图表、指标与关键位、快讯、预警与扫描，各自可以单独启动、单独使用，也可以一起用。
- 出策略时能快速取到数据。人在图表上看到的和策略拿到的是同一份、同一口径的数据。

## 已确认的需求

| 问题 | 回答 |
|---|---|
| 使用环境 | 本机，自己一个人用 |
| 出策略的方式 | 全部四种：Python 脚本/Notebook；agent 出策略；图表上写规则（类似 Pine）；图表上人工判断 |
| 快讯内容 | 全部四类：加密新闻、交易所公告、宏观日历、社交媒体 |
| 市场范围 | 加密 + 美股 |
| 最先要用起来的 | 数据 + 策略取数 |
| “快”的含义 | 两者都要：一两行代码就能取到数据，不用先启动一堆东西；实时行情到策略的延迟要小 |
| 策略近期做到哪一步 | 历史回测 + 模拟盘（原规划的 M3），暂不做实盘 |
| 单独启动的形式 | 由设计方建议 |

## 由需求推出的约束

- 同一份数据要同时供给图表、快讯页、策略脚本和 agent。存储只允许一个写者（ADR-0006/0011/0012），所以数据层很可能是常驻服务，其他功能作为它的使用方。
- 同一套策略代码要能跑回测、模拟盘和实时信号，否则“出策略”和“验证策略”会出现两套口径。
- 图表上写规则、Python 策略、agent 策略最终要走同一套指标算子（ADR-0010 的单一权威实现）。
- 本机单用户，不需要多用户鉴权和跨设备访问（与 [[defer-local-auth-hardening]] 一致）。

## 可以复用的现有部分

foundation（契约、算子、关键位引擎）、packs/feed/replay（行情接入与回放）、perception（冷热库、快照）、预警/扫描/会诊的业务逻辑、desk-ui 的各 feature 组件。

## 需要调研的空白

已有调研（`docs/research/`）覆盖了数据中心选型、OpenBB/Qlib、NautilusTrader 执行面、永续和宏观日历数据源、Alpaca。尚未覆盖：

1. 研究、回测、模拟、实时共用一套策略代码和取数接口的做法，以及低延迟取数（进程内调用还是 IPC）。
2. 本机常驻数据服务 + 多个可单独打开的前端的产品形态（浏览器多页面、桌面多窗口）。
3. 快讯数据源：加密新闻、交易所公告、社交媒体（X API 的成本和限制）。
4. 图表脚本：类 Pine 规则语言有哪些可用方案，能否复用 Python 算子。

## 调研结论（2026-11-20）

四份调研都在 `docs/research/`，每条结论附一手来源。核对情况：X API 定价已独立复核一致；CryptoPanic 价格页是浏览器端渲染，未能独立复核；`AlertCondition` 只能表达单个条件，已对照代码确认。

| 主题 | 文件 | 要点 |
|---|---|---|
| 统一策略运行时 | `unified-strategy-runtime-sources.md` | Nautilus、LEAN 都把策略和数据引擎放在同一进程，切换回测/模拟/实盘只换数据入口和成交组件；Notebook 和策略同口径靠同一段取数代码 + 同一批文件，不靠同一进程。三方案：策略进程内 / 独立进程（本机 WS + 直读 Parquet）/ 默认独立、可信策略进程内。建议先实测 K 线到策略回调的延迟（p50/p99）再定。 |
| 本机产品形态 | `local-multi-frontend-product-form.md` | 数据服务的生命周期应独立于窗口；macOS 用 launchd 用户级 Agent 负责登录常驻和崩溃重启。三形态：A 常驻服务 + 浏览器多页面（可装成 PWA）/ B 常驻服务 + Tauri 薄壳多窗口 / C 桌面应用托管 Python。A 和 B 共用前后端，可以先 A 后 B。 |
| 快讯数据源 | `news-feed-data-sources.md` | 交易所公告免费（OKX 时间戳最好，Bybit 无推送，Binance 只有需签名的 WS 且无历史）；免费且可合规给策略用的加密新闻基本没有（CryptoPanic 最低 $199/月或 $50/周）；X API 只按用量计费，$0.005/条，约 $75–300/月，且删改同步要求与冷库只追加冲突；Telegram 条款禁止 AI/ML 用途；美股免费组合为 Alpaca News + Finnhub + SEC EDGAR。 |
| 图表规则脚本 | `chart-rule-scripting-sources.md` | 照搬 Pine 的两条防前视规则（只在收盘柱求值；跨周期只看最近已收盘的大周期柱）；现成 Pine 实现均不适用（float、许可证或闭源转换服务，且违反 ADR-0010）；KLineChart v10 可显示后端算出的结果；不用受限 Python。三路线：JSON 表达式树（1–2 周）/ Pine 风格子集编译成表达式树（3–6 周，有条款灰区）/ 受限 Python。 |

## 已定决策

### D1 产品形态与进程模型（2026-11-20）

- **前端**：浏览器多页面。现有 FastAPI 在 127.0.0.1 同源托管 SPA，图表、快讯、预警、扫描等各有一个可直接打开的路由，可在多个标签页/窗口打开，或用 manifest 装成 PWA 独立窗口；页面间联动用 BroadcastChannel。DSH 插槽里的工作台保留为另一个使用方。以后需要原生多窗口时再加 Tauri 薄壳，前后端不重写。
- **后台**：一个常驻服务，由 launchd 用户级 Agent 负责登录启动和崩溃重启（需显式设 `ProcessType`）。行情、快讯采集、预警、扫描在同一进程，按配置开关；每项功能写自己独立的存储（沿用 ADR-0006 按写者分库），以后需要时可以拆成独立进程而不迁移数据。
- **不在本决策内**：策略运行位置（D2）。
- 否决：直接做桌面应用（要多维护打包签名，近期收益小）；桌面应用托管服务（关掉应用后脚本取不到数据）；按功能拆多个进程（要做跨进程行情分发和多进程启停，本机单用户收益不大）。

### D2 实测数据：K 线事件到策略回调的延迟（2026-11-20）

原型 `.scratch/prototype/latency/bench.py`（仅本地）。Apple M4、Python 3.15.2、FastAPI 0.164 + uvicorn 0.54（无 uvloop）、websockets 15。服务端仿 `desk_ws`：每客户端有界队列 256、`send_json(model_dump)`；客户端 `json.loads` + `KlineEvent.model_validate` 后回调。单位 µs，所有场景无丢弃。

| 负载 | 进程内直接回调 p50/p99 | 进程内 asyncio 队列 | 本机 WS 1 客户端 | 本机 WS 4 客户端 |
|---|---|---|---|---|
| 常态 10 条/s | 2 / 4 | 106 / 147 | 1006 / 1279（max 1663） | 1312 / 1767（max 3592） |
| 繁忙 200 条/s | 0.5 / 2 | 45 / 97 | 423 / 913 | 499 / 1029 |
| 突发连续 | 0.1 / 0.1 | 13 / 16 | 77 / 114 | 114 / 143 |

- 本机 WS 最坏约 1–2 ms（p99），偶发 3.6 ms；进程内为微秒级。
- 低速率反而更慢：空闲进程被唤醒的开销主导（推断：macOS 调度与 CPU 节能），不是传输本身。
- 未计入交易所到本机的网络延迟和服务端其他负载；单条 K 线负载。

### D2 策略运行位置（2026-11-20）

- **策略跑在独立的策略进程**，不进常驻服务。同一套策略代码，数据入口可替换：
  - 实时信号与模拟盘：订阅常驻服务的本机 WebSocket（实测额外延迟约 1–2 ms p99）。
  - 回测：在策略进程内直读历史 Parquet 按时间回放，不经过服务。
  - Notebook：同一段取数代码、同一批文件，与策略同口径（参照 LEAN QuantBook 的做法）。
- 理由：延迟差相对交易所网络延迟和分钟级策略可以忽略；策略（尤其 agent 生成的）卡死或崩溃不能拖垮行情服务和图表。
- 否决：放进常驻服务（隔离差）；混合模式（省下约 1 ms 无实际价值，却要维护两种运行方式）。
- 留给 D3：取数接口的具体形状、WS 积压与断线补数的语义、模拟盘的成交模块放在哪一侧。

### D3 统一取数接口与历史数据存储（2026-11-20）

依据：`docs/research/data-access-and-numeric-types.md`、`fill-simulation-and-tick-data.md`、`ducklake-evaluation.md`、`unified-strategy-runtime-sources.md`。

- **历史读取**：SDK 按清单直接读 Parquet；冷库尚未写入的最新几根向常驻服务取并按时间戳拼接去重；服务未运行时只用本地数据。所有查询支持 `as_of`，按 `ts_available <= as_of` 截断（参照项目都不提供这种截断，需自己实现）。先例：Nautilus、LEAN、ArcticDB、OpenBB 都由调用方自己读存储。
- **冷库持续写入**：常驻服务在每根 K 线收盘后写入尾部小文件，定期合并进分区文件，并在清单中原子切换；旧文件延迟删除。需修订 ADR-0011（原“快照冻结才发布”的前提已不成立）。
- **清单**：继续自写（在现有 `cold_store` 上扩展），暂不采用 DuckLake；文件结构保持可迁移。否决 DuckLake 的理由：所有读者必须经 DuckDB、跨版本兼容事故（#1924 未修）、flush 静默回滚的未解释现象。
- **目录布局**：K 线按 `标的/周期/月` 分区，逐笔与盘口按 `标的/日` 分区；另设衍生品、美股公司行为（读取时按 `as_of` 复权）、快讯数据集。
- **数值存储**：每个标的一个文件，价格数量用 `decimal128(18, 该标的精度)` 并以 INT64 物理存储（实测 100 万行约 22 MB、读 11 ms、转 float 11 ms，精确、无尾零）。列：`ts_event`、OHLCV/turnover、`ts_available`、`ts_ingested`、`ts_committed`（int64 毫秒）、`precision`（字典编码）、`revision`（预留）。
- **SDK 返回**：策略与指标拿精确 Decimal 契约对象；`.to_frame()` 给 float DataFrame 供研究（先例 Nautilus/LEAN 同为双入口）。
- **实时订阅语义**：图表页面仍是满了丢最旧；策略订阅不静默丢弃，队列满则断开，客户端按最后收到的时间戳补齐。
- **模拟成交**：放在策略进程内，回测与模拟盘共用同一成交模块；策略进程自己写账本库，服务只读用于展示（先例 Nautilus Sandbox、LEAN PaperBrokerage）。
- **高频数据**：对实时订阅的少数标的落盘买一卖一 + 逐笔成交（BTC 永续估算约 30–65 MB/天）；需新增订阅 `publicTrade.{symbol}`；逐笔历史从 Bybit 公开归档 `public.bybit.com` 按日补；多档盘口暂不存。定存储预算前先落盘 1–2 周实测。
- **快照**：保留，用于固定 agent 会诊和预警触发时的证据；日常取数不再需要先建快照。HTTP 接口新增按时间范围取数，DSH 工具与 SDK 共用同一套契约。
- 2026-11-22 的两轮持续写入及合并实测共执行 153 次 SDK 查询。13 次少柱，均标记为 `tail_completed=False`，重柱和文件读取错误均为 0。慢读者在 24 小时和 3 代更新条件均满足后遇到旧文件已回收，重读清单一次即返回完整结果。保留现有回收规则。两次清单换代可让 SDK 丢弃服务已返回的未落盘柱，详见 [data-access/09](../data-access/issues/09-preserve-sdk-tail-during-manifest-churn.md)。
- 2026-11-22 实测千万行的 Arrow IPC 和 JSON 分别为 1.21 GB 和 2.29 GB，本机 HTTP 匿名套接字传输中位数分别为 1.22 秒和 2.13 秒，解析为各自原生结构分别为 0.076 秒和 8.92 秒。现有范围接口每次最多 10,000 根，保留 JSON，大批量本机历史沿用 SDK 直读 Parquet。若后续有百万行级 HTTP 导出需求，先用 TCP 回环复测，再决定是否提供 Arrow IPC 流。完整结果见 [data-access/05](../data-access/issues/05-measure-tail-consistency-and-arrow.md#实现记录2026-11-22)。
- data-access/07 按生产 Parquet 布局落盘了一个合成 UTC 日，BTCUSDT 逐笔与买一卖一各 64,000 条。逐笔 2,498,132 字节（含 16 字节成交 UUID；去掉该列为 1,353,374 字节），买一卖一 1,571,294 字节。UUID 用于同毫秒成交区分及归档补缺。首个真实完整实时日的容量待用 `talaria cold-size --day YYYY-MM-DD --data-dir <目录>` 采集。命令统计当前清单引用的 Parquet 体积。实测步骤见 [data-access/07](../data-access/issues/07-trades-and-bbo-storage.md#实现记录2026-11-22)。

### D4 指标、信号、策略的统一组件模型（2026-11-20）

原则：未来会发展到什么程度不确定，框架只固定少数核心契约，写法和实现方式全部可插拔，不在框架层限制死。

**固定的核心（改动需要新 ADR）：**

1. **组件接口**：指标（输出数值序列）、信号（输出事件）、策略（输出下单意图）三类，上一类可引用下一类；每个组件带元数据：输入、参数及取值范围（供以后寻优使用）、输出类型、版本。
2. **运行时保证**：组件只能通过运行时上下文 `ctx` 取数据，`ctx` 按当前时刻 `as_of` 截断，计算只在 K 线收盘后进行；跨周期只能看到大周期最近一根已收盘的柱（照搬 Pine 的非重绘规则）。防前视由运行时负责，不依赖写法。
3. **算子注册表**：指标算子以 `foundation/operators` 的 Decimal 实现为唯一权威（ADR-0010），新算子注册时必须附黄金测试向量。

**可插拔的部分（以适配器方式增加，不改核心）：**

- 写法：先实现 Python（在独立策略进程运行）和带版本号的 JSON 规则（可在常驻服务运行，用于图表规则、预警、扫描）；以后可加文字语法、Pine 风格子集、其他语言等，都编译或适配到同一组件接口。
- 运行位置：JSON 规则只调用已注册的算子，可安全运行在服务内；任意代码只运行在隔离进程，agent 生成代码的额外限制在 D6 定。
- 展示：图表通过后端计算结果显示任意组件的输出（KLineChart v10 异步 calc）。

**第一步**：定义组件接口与 Python 写法；把现有单条件的 `AlertCondition` 升级为 JSON 规则，并配图表规则编辑器。

依据：`docs/research/chart-rule-scripting-sources.md`。否决：只用受限 Python 作为规则语言（RestrictedPython 官方声明不是沙箱）；采用现成 Pine 实现（float、许可证或闭源转换服务，且会形成第二套算子）。

### D5 快讯（2026-11-20）：暂时不做

- 本轮不实现快讯，也不接任何数据源。
- 保留的设计约束（以后做时直接沿用）：统一快讯契约（来源、类别、标题、摘要、链接、相关标的、`ts_event`/`ts_published`/`ts_available`/`ts_ingested` 及精度等级）；每个数据源一个插件；Parquet 按来源/日分区，由常驻服务写入；每条标记能否供策略和 agent 使用（条款只允许人看的来源仅展示）；删除同步用追加“已删除”标记 + 定期重写分区。
- 备选首批：零成本组合（交易所公告、宏观日历、Alpaca/Finnhub/EDGAR，媒体 RSS 仅展示）；加 X 约 $75–300/月；再加 CryptoPanic 约 $199/月。Bybit 公告接口在本机地区被 CloudFront 封锁，届时需实测。依据：`docs/research/news-feed-data-sources.md`。

### D6 交易流水线：账户进程作为插件宿主（2026-11-20）

D2 的“策略进程”扩展为**账户进程**：承载一个或一组子账户的策略、定仓、风控、成交和账本。一个**交易方案**就是一份配置，为每个插槽选定插件；不同方案只换配置，不改框架。

**插槽（可插拔）：**

| 插槽 | 首批默认插件 | 以后可加 |
|---|---|---|
| 数据入口 | 实时本机 WS；回测 Parquet + 虚拟时钟 | 其他数据源 |
| 策略 | D4 组件：Python 策略、JSON 规则、agent 交易计划、`ControllerPatch` 参数调整 | 其他写法 |
| 定仓 | 按止损距离定仓（原 L3 R 定仓） | 名义金额、波动率、目标权重 |
| 风控 | 原七步风控 + 单一仓位回合不变量 | 网格、定投、组合再平衡等所需规则 |
| 成交 | 1m K 线模拟（原六条诚实仿真法则，同根 K 线先止损）；盘口加逐笔模拟 | 实盘接口（ADR-0003 的 Execution Seam） |
| 工具 | agent 可调用的工具集（取数、算指标、出计划） | 按方案开放不同工具 |

**固定的底线（改动需要新 ADR）：**

1. 事件顺序与时钟：数据 → 策略 → 定仓与风控 → 成交 → 记账，回测与实时同一时钟语义；组件取数一律经 `ctx` 截断。
2. 开仓、加仓、放宽止损必须经过风控插槽；只减风险的操作（收紧止损、减仓、平仓、撤未成交入场单、切 REDUCING/HALTED）可直达成交。人工、agent、策略三种来源同样适用。
3. 账本格式统一，每个子账户的账本只有一个写入方（ADR-0006），不同方案的结果可以放在一起对比和复盘。
4. 插件接口带版本号，插件声明兼容的接口版本。

**连接方式：**

- 图表人工下单和 agent 会诊产出的计划草案，由常驻服务转发给对应的账户进程；常驻服务只读账本用于展示。
- 回测与模拟盘是同一个账户进程，只换数据入口；原设计中的 `replay_runner`、`study_optimizer`（Optuna，ADR-0007）以批量启动账户进程的方式实现。

**agent 生成代码的限制：**

- agent 默认产出交易计划、JSON 规则或参数调整，都经过风控插槽。
- agent 写的 Python 策略可以自由回测；进入模拟盘前需要人工批准，并在资源受限的独立进程中运行。
