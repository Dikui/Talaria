# 产品按功能组织：一个 launchd 常驻服务 + 浏览器多页面

Talaria 从“一个整体工作台”改为按产品功能组织：行情数据、图表、指标与关键位、预警、扫描等功能各自可以单独打开，也可以组合使用，参照 TradingView 的使用方式。本机单用户。决定：

- **后台**：一个常驻服务，由 launchd 用户级 Agent 负责登录启动和崩溃重启（plist 显式设置 `ProcessType`）。行情采集、冷库写入、预警、扫描在同一进程，按配置开关。存储沿用 ADR-0006 按写者分库：冷库、快照库各一个库；预警、自选、画线、标注、简报等协同状态仍集中在服务拥有的协同状态库，由同一个写队列写入（ADR-0012）。以后某项功能真要拆成独立进程时，再把它的表迁到自己的库。服务启动时持有数据目录的排他锁，同一数据目录只能有一个服务实例；其他需要写协同状态的命令（如用量补录）在服务运行时经服务接口提交，服务未运行时先取得同一把锁再直接写。
- **前端**（已被 ADR-0020 取代：DSH 为主入口，浏览器多页面只作离线兜底）：浏览器多页面。服务在 `127.0.0.1` 同源托管 SPA，每个功能一个可直接打开的路由，可以开在多个标签页或窗口，也可以用 Web App Manifest 装成 PWA 独立窗口；页面间联动用 `BroadcastChannel`。DSH 插槽中的工作台保留为另一个使用方（ADR-0005 不变）。
- 策略不在常驻服务里运行，见 ADR-0015。

数据服务的生命周期独立于任何窗口：关掉所有页面后，Notebook 和策略仍能取到数据。

## Considered Options

- **直接做桌面应用（Tauri/Electron 多窗口）**：多维护打包、签名和自动更新，近期收益小。以后需要原生多窗口时在浏览器方案外加 Tauri 薄壳，前后端不重写。暂缓。
- **桌面应用托管 Python 服务**：关掉应用后脚本取不到数据，违背“数据随时可取”。否决。
- **按功能拆成多个进程**：要做跨进程行情分发和多进程启停，本机单用户收益不大。否决。
- **现在就按功能拆库**：协同状态的各领域共用一个写队列，拆库只会多出跨库一致性问题，眼下没有收益。否决；拆进程时再迁。

## Consequences

- `talaria up` 的前台模式保留用于开发和回放验收；日常使用改为安装 launchd Agent 后常驻。
- 每个功能页面必须能在只打开它自己的情况下工作，不能假设同一页面里有其他功能的状态。
