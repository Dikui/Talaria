# 采用多虚拟子账户单标的单一仓位回合模型与按写者物理分库

系统支持在同一行情底座上创建多个资金、保证金与风险配额完全隔离的虚拟子账户（`Sub-Account`），并强制执行“同一虚拟子账户在同一交易标的上同一时刻最多存在一个方向的活跃仓位回合（`Position Round`）”不变量：同向获批加仓合并入当前活跃 `PositionExecutor` 统一管理保护屏障与回合归因，反向开仓草案在组合风控层默认拒单（须先结清当前回合）；多策略并行或人机独立对照通过拆分不同虚拟子账户实现。本地持久化不引入外部数据库服务，而是按进程内唯一写者物理拆分为 5 个独立 SQLite 库（冷库清单库、实时冻结快照库、协同与感知状态库、多子账户复式账本库、寻优注册库）配合 `Optuna JournalStorage` 追加日志。

## Considered Options

- **允许同一子账户同标的并行运行多个独立 `PositionExecutor`（包括多空对锁或不同止损位的独立子单）**：表面灵活，但在永续净头寸加权均价或美股 `FIFO` 批次复式账本下，后开先平子单的独立瀑布归因与账本真实结转盈亏在数学上无法恒等对齐，且反向计划成交会直接冲销底层净持仓导致存量 `reduce_only` 屏障悬空失效。
- **单机共用单一 `talaria.db` SQLite 文件或引入本地 PostgreSQL 容器**：单一 SQLite 文件在实时行情模拟撮合、前端高频画线保存、后台快照归档与多进程参数寻优并发写入时必现 `SQLITE_BUSY` 锁竞争；引入 PostgreSQL/Docker 则违背个人单机零重型中间件、开箱即用的维护约束。

## Consequences

- 执行层的仓位回合、复式账本的已实现盈亏与评测模块的六维全成本归因（含子账户级全量认知 Token 成本）实现逐笔精确对齐。
- 每个 SQLite 库均由单一异步写协程或主进程独占顺序写入，多进程 `Optuna` Worker 仅在内存中运行临时账本并向文件锁日志追加结果，彻底消除跨模块写锁争用。
