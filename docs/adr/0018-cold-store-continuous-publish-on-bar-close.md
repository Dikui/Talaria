# 冷库在每根 K 线收盘后持续写入，取代快照冻结触发

ADR-0011 让冷库只在快照冻结时发布，前提是 v1 没有独立的实时采集循环、也没有人在快照之外取数。ADR-0014 引入了常驻服务，ADR-0016 让 SDK 直读 Parquet，这个前提不再成立：没有人创建快照时冷库就不更新，策略和 Notebook 读到的历史会落后。

决定：常驻服务在每根 K 线收盘（`confirmed`）后把它写入该分区的尾部小文件；定期把尾部文件合并进分区文件，并在 `data_manifest.sqlite` 中用短事务原子切换清单。服务仍是冷库的唯一写者（ADR-0006）。快照保留，只用于固定 agent 会诊和预警触发时的证据。

冷库有两条写入路径，都由服务的同一个冷库写入器执行：

1. **实时收盘**：每根 `confirmed` 柱写入尾部文件。
2. **历史回填**：服务按需用 REST 回填服务启动前的历史（图表或 SDK 请求的范围缺数据、启用实时订阅的标的启动时补齐），直接写入冷库，不经快照。

保留 ADR-0011 的约束：冷库写入失败只记 warning，不阻塞行情和图表；读者只读清单显式列出的文件。

## 修订与时点

同一根柱可能被发布多次（迟到修订、REST 回填覆盖实时推送）。为了让过去时点的查询在合并、重启前后结果不变：

- **每个修订单独保存一行**，带自己的 `revision` 与 `ts_available`。首次可见的已收盘版本 `ts_available` 为柱结束时刻；之后的修订 `ts_available` 为服务实际收到它的时刻，而不是柱结束时刻。
- **合并不丢修订**：合并只重排文件，不按时间戳去重。
- **读取时先截断、再选版本**：先按 `ts_available <= as_of` 过滤，再对每个 `ts_event` 取 `revision` 最大的一行。省略 `as_of` 时即取最新修订。这一实现只有一份，SDK、范围接口和 `ctx` 共用（ADR-0016）。

## 旧文件与慢读者

被合并替换的文件不立刻删除，至少保留最近若干代清单且不少于一个保留期（默认 24 小时）。读者按打开时的清单版本读取；读到的文件已被删除时，整次查询按最新清单重试一次，仍失败才报错。不做跨进程的读租约。

## Considered Options

- **保持快照触发**：冷库延迟取决于有没有人看盘，SDK 直读拿不到最近数据，补尾范围不可控。否决。
- **每根 K 线直接改写分区文件**：Parquet 不支持追加，每分钟重写整月文件成本随历史增长，还会和读者争用同一文件。否决。
- **合并时同一时间戳后出现者胜**：存储最省，但过去时点的查询会在合并后返回之后才出现的修订。否决。
- **读者向服务登记读租约，服务等租约释放再删文件**：能精确保护慢读者，但服务未运行时 SDK 无处登记，且要处理崩溃读者的残留租约。否决；保留期加重试已够本机单用户使用。

## Consequences

- 不再需要 ADR-0011 说的“放宽游标”。
- 现有实时解析把 `ts_available` 固定为柱结束时刻，需要按上面的规则区分首个版本和之后的修订。
- 历史回填原本由 `SnapshotBuilder` 随快照发布，改为冷库写入器的独立路径。
- 待实测：服务补尾与 SDK 直读在并发读写下的一致性。
