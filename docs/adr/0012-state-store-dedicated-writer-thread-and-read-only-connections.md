# 状态库写入走专用写线程，读取用只读连接绕过写队列

工作台状态库（`state.sqlite`）以 `synchronous=FULL` 保证人工画线、预警、会诊等记录落盘不丢，每次提交都要 fsync。原先 `StateWriterQueue` 在事件循环里直接执行 SQLite，fsync 期间整个 API 和行情推送都会停顿，读请求也要排在写请求之后。现决定：写操作仍由单个协程按提交顺序派发，但实际执行放到一个只有一个线程的专用执行器上，并独占唯一的写连接；读操作不进写队列，每次在默认线程池里打开 `mode=ro` + `query_only` 的只读连接，借 WAL 读取已提交的数据。

## Considered Options

- **继续在事件循环里同步执行**：实现最简单，但 fsync 会阻塞所有协程，行情推送和看盘请求随写入频率抖动。否决。
- **每次写都丢进通用线程池**：不阻塞事件循环，但多个线程各自持有写连接，提交顺序无法保证，SQLite 还会出现写锁竞争。否决。
- **引入 aiosqlite 等异步驱动**：内部同样是“每连接一个线程”，换来的只是多一个依赖，读写分离和单写者约束仍要自己做。否决。
- **读也走写队列**：天然读到自己刚写的数据，但读会被慢写堵住，正是要解决的问题。否决。

## Consequences

- 写入顺序只由写队列保证；仓储代码不得在写队列之外打开写连接，`claim_writer` 会拒绝同一库的第二个写者。
- 读取只能看到已提交的数据。需要“写后立即读到自己结果”的流程，要么让写操作直接返回结果，要么在写操作完成后再发读请求。
- 每次读都新开只读连接，开销换来无共享状态；若以后读量大到成为瓶颈，再考虑只读连接池，而不是让读回到写线程。
