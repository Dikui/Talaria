01 / Provider adapters

数据接入

把供应商差异留在 Adapter 内，让上层面对稳定的数据能力，而不是一组互不兼容的 API。

输入IngestRequest · 授权凭据 · Cursor
输出RawBatch · SourceMetadata · FetchReceipt

第一版要实现

  • 一个市场、一个明确 feed、一个供应商。
  • 完整分页、限流退避、超时重试与断点续传。
  • 声明修订、退市、复权和流式能力；不可静默降级。
供应商密钥仅在接入层使用；不交给 Agent。抓到数据不等于数据已发布给消费者。
模块名与契约均为 Talaria 的拟议设计。
事实 ≠ 摘要

原始内容与具体版本是依据。LLM 总结、特征和 embedding 不能代替原文。

数据源 ≠ 业务接口

用 Adapter 隔离来源变化，但不把不同 feed、复权和覆盖口径伪装成相同数据。

质量门禁 ≠ 零值填充

停牌、休市、无成交、无权限和接口故障，要返回不同状态。

02 / Point-in-time explorer

同一份财报，为什么有两个历史？

移动决策时点，比较「市场历史可知」与「系统实际观察」。

固定快照解决复现。
可用时间与历史版本解决前视偏差。

报告期结束 ≠ 信息已经可见

03 / Storage & publication

三个组件，各司其职。

不是把行情重复存三份，而是分开「内容、事务元数据、查询计算」。

01 / CONTENT

Parquet

保存不可变分析数据

标准化行情、财务事实、公司行动和文档元数据。按 dataset / market / feed / timeframe / 时间组织批次。

文件格式，不自带全目录事务或 PIT。
02 / CONTROL

SQLite

管理发布与快照清单

任务、游标、版本、manifest、质量结果和授权配置。第一版采用本地、受控单发布者。

不作为海量行情的第二份主存。
03 / QUERY

DuckDB

查询固定的文件集合

依据 manifest 显式文件列表读取 Parquet，进行过滤、聚合和质量分析；查询规则也随快照固定。

动态目录 glob 不是冻结快照。
DuckDB：显式文件列表与下推 ↗SQLite：本地、单写入者边界 ↗原始 JSON / 正文另存文件或对象；仅在许可允许范围留存。

可靠发布：先把内容写稳，再让它可见。

这是待实现、待崩溃测试的协议，不是 Parquet 或 DuckDB 的自动保证。

01锁定任务从已提交游标开始
02采集与 staging归档原文、规范化
03质量检查失败批次隔离
04新文件持久化校验 hash、同步目录
05 / COMMIT提交 manifest短事务更新版本与游标
06新快照可见旧快照仍指向旧文件
崩溃、修订与恢复，需要证明什么？
  • 文件写好但事务未提交：只留下不可见的孤儿文件；不能让消费者读到半批数据。
  • manifest 已提交：恢复后所有引用文件必须存在且 hash 一致；备份要覆盖元数据和文件集，不能只复制数据库。
  • 重跑与修订：同一任务不重复发布；真实修订是新版本，不能被去重吞掉。游标只能随成功发布推进。
  • 保留与撤权：文件合并、垃圾回收要检查快照引用；法律删除或撤权时，明确标记快照不可再提供，不伪造可复现。
何时加 Dagster？

依赖、回填与运行观察复杂后。起步用 CLI；定时运行由未来部署配置，本页不创建任务。

何时换 PostgreSQL？

多主机写入、多人审计或写入排队成为真实问题后，不用网络共享 SQLite 文件硬撑。

何时上对象存储？

跨机器共享、容量和耐久性要求出现后。不可变 key＋元数据发布，不能照搬本地 rename。

05 / Build in three stages

先跑通一种数据，再扩展能力。

不先建设全市场、全频率、全类型的数据平台。以下是建议阶段与验收条件，尚未实施。

01PRICE FIRST

可靠的历史价格切片

一个市场、一个 feed、日线、受控证券范围；原始价格＋必要公司行动与交易日历。

Adapter → 标准化 → 质量 → 固定快照
EXIT CRITERIA
  • 同一快照重跑，文件与查询结果一致。
  • 分页完整，任务重跑不重复发布。
  • 新数据或修订不改变旧快照。
  • 没有历史修订或退市覆盖时，明确限制。
02ONE EVIDENCE SOURCE

一条文本 / 财报链路

从财报或新闻中选一种；原文、版本身份、可用时间与证据引用完整串联。

原文 → 版本 → 时点证据 → 只读检索
EXIT CRITERIA
  • 修订前后查询各自可见的版本。
  • 未知时间不能自动通过 PIT 检查。
  • Agent 观点能追溯具体原文版本。
  • 检索和外部模型处理符合授权。
03PAPER OPERATIONS

增量更新与持续运行

补齐迟到修订、恢复、新鲜度告警、系统实际观察回放和备份演练。

增量 → 发布 → 告警 → 回放 / 恢复
EXIT CRITERIA
  • 崩溃恢复后引用文件全部可验证。
  • 关键数据过期时拒绝可交易信号。
  • 不悄悄换供应商、feed 或复权口径。
  • 确有需要时再增加 Dagster / 服务化。
完整验收清单 · 八项必须能证明的行为
  1. 同一 snapshot_id 的文件 hash、修订选择和查询结果一致。
  2. 初版和修订版按各自可用时间选择，未知时间显式拒绝或降级。
  3. 10:01:10 才提交的 bar 不出现在 10:01:00 的实际观察回放里。
  4. 分页或限流重试不跳页、不重复事实；游标随发布提交。
  5. 夏令时、半日市、拆股、代码变更、退市等有固定测试样本。
  6. manifest 提交前崩溃不可见，提交后全部文件存在且 hash 正确。
  7. 合并与回收不破坏有效快照；撤权/删除使快照显式不可提供。
  8. 过期、异常、无权限不静默变零；Agent 无写权限与密钥访问权。

06 / Contract before complexity

用小接口，隔离复杂的数据现实。

以下是拟议接口，不是某个开源工具已经提供的完整 API。

Read interface / proposed
create_snapshot(request: SnapshotRequest)
    → EvidenceSnapshot

read_bars(snapshot_id: str, query: BarQuery)
    → BarResult

read_facts(snapshot_id: str, query: FactQuery)
    → FactResult

read_documents(snapshot_id: str, query: DocumentQuery)
    → DocumentResult

get_quality(snapshot_id: str)
    → QualityReport

读取契约统一；供应商、文件格式和索引实现可在内部替换。禁止通过任意 SQL / URL 绕过快照与权限。

快照固定什么？

  • 范围：历史证券集合、事件窗口、数据版本、feed 与复权口径。
  • 时点：知识截止时刻、历史可知 / 实际观察模式，以及可用性证据规则。
  • 内容：不可变文件列表、hash、schema 与转换版本。
  • 质量：缺失、过期、覆盖范围和允许的降级策略。
查询只能缩小范围，不能偷偷读最新。
新增数据需要新快照。数据没有历史修订，不能用一个时间戳“补造”过去。
